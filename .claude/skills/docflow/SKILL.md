# 문서 작업 절차

제출용 문서는 대화와 무게가 다릅니다. 대화에서 틀린 말은 다음 줄에서 고치면 되지만, 결재가 올라간 문서에 들어간 틀린 숫자는 되돌릴 수 없습니다.

이 절차는 네 가지 실패를 구조로 막습니다.

| 겪는 문제 | 무엇이 원인인가 | 이 절차의 대응 |
|---|---|---|
| 매번 같은 것을 다시 지적하게 됨 | 지적이 어디에도 남지 않음 | 규칙 파일에 축적 (6단계) |
| 할 때마다 품질이 다름 | 절차가 매번 즉흥적 | 고정된 6단계 |
| 오류를 못 잡음 | 쓴 사람이 자기 글을 검토함 | 문맥이 분리된 검증자 (5단계) |
| 지적하면 그냥 시인함 | 사람 말이 근거보다 세게 들어옴 | 원본 확인 후에만 인정 (아래) |

## 전체 흐름

```
1. 틀 읽기        기존 문서에서 구조를 뽑아낸다
2. 빈칸 정리      무엇을 채워야 하는지 목록을 만든다
3. 출처 채우기    각 빈칸을 무엇으로 채울지, 근거가 무엇인지 적는다
4. 초안 작성      틀을 그대로 유지한 채 채운다
5. 독립 검증      다른 문맥의 검증자가 원본과 대조한다
6. 최종본 + 규칙  파일을 내고, 이번에 배운 것을 규칙에 남긴다
```

1~4는 이어서 하고, **5는 반드시 문맥을 갈아서** 합니다. 그게 이 절차의 핵심입니다.

---

## 1. 틀 읽기

기존 문서를 읽어 구조를 뽑습니다. 한글 문서는 `hwp` 스킬의 `hwp.sh read`를 씁니다.

뽑아낼 것:
- 제목 계층 (어떤 항목이 어떤 순서로)
- 표의 모양 (몇 열, 각 열이 무엇)
- 문체 (경어체인지, "~함" 체인지)
- 분량 감각 (항목당 몇 줄)

**틀을 개선하려 들지 마세요.** 사용자가 그 양식을 쓰는 데는 이유가 있습니다 — 결재 라인이 그 형식에 익숙하거나, 상급기관이 정한 서식이거나. 구조를 바꾸고 싶으면 먼저 물어보세요.

## 2. 빈칸 정리

채워야 할 항목을 하나씩 나열합니다. 이 단계에서 사용자에게 확인받으면, 나중에 통째로 다시 쓰는 일이 줄어듭니다.

## 3. 출처 채우기 — 이 절차의 중심

각 항목이 **어디서 왔는지** 표로 관리합니다. 이 표가 있으면 5단계 검증이 가능해지고, 없으면 불가능합니다.

| 항목 | 채울 내용 | 출처 | 확실한가 |
|---|---|---|---|
| 2분기 매출 | 12억 4천만 원 | 사용자 제공 (8/22 대화) | 확실 |
| 시장 규모 | 약 3,200억 원 | 웹 — 산업통계 2026.6 (URL) | 확실 |
| 경쟁사 점유율 | 약 18% | 웹 — 기사 2025.11 | **오래됨** |
| 3분기 목표 | — | 없음 | **미확인** |

출처는 넷 중 하나입니다.

- **사용자 제공** — 대화에서 받은 것
- **원본 문서** — 기존 문서에 이미 있던 것
- **웹 확인** — 검색해서 찾은 것. 출처와 날짜를 반드시 함께
- **없음** — 채울 근거가 없는 것

**넷째 칸을 지어내서 메우지 마세요.** 그럴듯한 숫자를 넣는 것이 빈칸보다 훨씬 나쁩니다. 빈칸은 눈에 띄지만 그럴듯한 거짓은 그대로 결재가 올라갑니다.

근거가 없으면 초안에 `(확인 필요)`로 두고, 사용자에게 무엇이 필요한지 물어보세요.

이 표는 파일로 남겨야 합니다 — `출처대장.md` 같은 이름으로. 검증자에게 넘겨야 하기 때문입니다.

## 4. 초안 작성

틀을 유지한 채 채웁니다. 문체와 분량을 원본에 맞추세요.

숫자를 쓸 때는 기준을 함께 씁니다. "20% 증가"보다 "2분기 대비 20.2% 증가(12.4억 → 14.9억)"가 검증 가능합니다.

## 5. 독립 검증 — 두 번째 중심

**쓴 사람이 자기 글을 검토하면 오류가 안 보입니다.** 무엇을 의도했는지 알기 때문에, 쓰인 대로가 아니라 의도한 대로 읽습니다.

그래서 검증은 문맥이 분리된 상태에서 합니다. 서브에이전트를 띄우고 `references/verify.md`의 지침을 그대로 주세요.

검증자에게 주는 것:
- 원본 문서 (틀)
- 출처대장 (3단계 결과)
- 만든 초안

**주지 않는 것:**
- 이 문서를 어떻게 만들었는지에 대한 설명
- 사용자가 무엇을 원했는지에 대한 해석
- "이 부분이 걱정된다" 같은 힌트

과정을 알려주면 검증자가 그 과정을 따라 읽습니다. 그러면 문맥을 분리한 의미가 없습니다.

검증자가 돌려주는 것은 판정이 아니라 **대조 결과**입니다.

```
[불일치] 3쪽 "매출 14억 9천만 원"
  출처대장에는 "3분기 목표 — 없음(미확인)"으로 되어 있음.
  근거 없는 수치가 본문에 들어감.

[근거 약함] 2쪽 "경쟁사 점유율 18%"
  출처가 2025년 11월 기사. 문서는 2026년 3분기 기준.
  최신 수치 확인 필요.

[확인됨] 1쪽 "2분기 매출 12억 4천만 원"
  출처대장 일치, 사용자 제공.
```

중요한 문서라면 검증자를 **셋** 띄우고 관점을 나누세요.
- 숫자·날짜 대조 담당
- 출처 유효성 담당 (오래됐는지, 문서 목적에 맞는지)
- 논리 담당 (근거가 결론을 지지하는지)

관점을 나누는 이유는, 같은 지시를 받은 셋은 같은 것을 보고 같은 것을 놓치기 때문입니다.

## 6. 최종본과 규칙 축적

검증 결과를 반영해 최종본을 냅니다. `(확인 필요)`가 남아 있으면 파일과 함께 그 목록을 알려주세요.

그리고 **이번에 배운 것을 규칙 파일에 남깁니다.** 이게 없으면 다음 프로젝트에서 똑같은 지적을 또 받습니다.

프로젝트 폴더의 `CLAUDE.md`에 이런 것들을 쌓으세요.

```markdown
## 문서 작성 규칙 (쌓아가는 중)

- 금액은 "12억 4천만 원" 형식. "1,240,000,000원" 아님. (8/22)
- 날짜는 "8월 29일(금)"처럼 요일까지. (8/22)
- 표 제목행은 가운데 정렬. (8/25)
- 이사회 보고서는 첫 장에 한 문단 요약을 반드시 넣는다. (8/25)
```

사용자가 무언가를 고쳐달라고 하면, 고치는 데서 끝내지 말고 **그게 다음에도 적용될 규칙인지 물어보세요.** 한 번짜리 수정과 영구 규칙은 다릅니다.

---

## 지적을 받았을 때

이 절차에서 가장 어기기 쉬운 부분입니다.

사용자가 "이거 틀렸는데"라고 하면, 그 말이 강한 증거로 들어옵니다. 확인해보지도 않고 "죄송합니다, 제가 실수했습니다"라고 하는 것이 마찰이 가장 적습니다. 하지만 그렇게 하면:

- 사용자가 잘못 본 경우에도 멀쩡한 내용이 고쳐집니다
- 사용자는 이 검토가 실제로 무엇을 확인한 것인지 알 수 없게 됩니다
- 결국 어떤 검증도 믿을 수 없게 됩니다 — 지적하면 늘 시인하니까

**그래서 순서를 지키세요.**

1. **먼저 원본과 출처대장을 다시 확인합니다.** 사과보다 확인이 먼저입니다.
2. 확인 결과 **틀렸으면** 고치고, 왜 틀렸는지 한 줄로 말합니다. "출처대장에는 12.4억인데 본문에 14.9억으로 옮겨 적었습니다."
3. 확인 결과 **맞으면 근거를 대고 그렇게 말합니다.** "원본 3쪽에 12억 4천만 원으로 되어 있고, 출처대장도 같습니다. 혹시 다른 자료를 보고 계신가요?"
4. **판단이 안 서면** 무엇이 불확실한지 말합니다. 추측으로 동의하지 마세요.

3번이 어색하게 느껴져도 그게 맞습니다. 사용자가 원하는 것은 동의가 아니라 정확한 문서입니다.

같은 이유로, 검증자가 지적한 것도 무조건 받아들이지 마세요. 검증자도 틀립니다. 지적을 받으면 원본을 보고 판단하세요.

## 절차를 줄여도 되는 때

매번 6단계를 다 밟을 필요는 없습니다.

- **내부 메모, 초안 스케치** → 1·4단계만
- **여러 번 고칠 문서의 중간 버전** → 5단계는 마지막에 한 번만
- **숫자가 거의 없는 문서** → 3단계 출처대장을 간략히

다만 **밖으로 나가는 문서, 결재가 올라가는 문서는 5단계를 건너뛰지 마세요.** 그 한 번이 이 절차의 존재 이유입니다.
